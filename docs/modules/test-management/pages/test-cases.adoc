= Test Cases

== Overview

A Test Case represents a reusable test flow. Test Cases store the interactions captured during a session and serve as the definition used for automated execution. Once created, a Test Case can be run repeatedly without recreating the original session.

Test Cases have one of three source types:

* *Manual* — created from a captured manual session.
* *Automation* — created from a completed Appium automation session.
* *Mixed* — created from a completed mixed session that combines manual and automation steps.

All source types appear together in the Test Case list and share the same core actions. Some capabilities differ by source type, as described in xref:test-management:test-cases.adoc#_test_cases_from_automation_sessions[Test Cases from automation and mixed sessions].

[#_convert_to_test_case]
== Convert a session to a Test Case

Test Cases are created by converting completed sessions. The following session types are convertible:

* Manual sessions
* Appium automation sessions
* Mixed sessions, which combine manual and automation testing in a single session

A session must be complete before it can be converted. Sessions that are still running are not eligible.

The following session types are not convertible:

* Revisit sessions
* XCUITest sessions
* UIAutomator sessions
* Gaming and GameDriver sessions
* Emulator sessions

For automation and mixed sessions, set the `kobiton:scriptlessCapture` capability in your Appium script. Without it, Kobiton captures limited session data.

You can convert a session to a Test Case from either of the following locations:

* Session Explorer, after a completed session
* Test Management, by selecting *New Test Case* and choosing from the list of completed sessions

In Test Management, completed sessions are listed from newest to oldest. Select the session you want to convert, then select *Convert*.

In both cases, the captured interactions from the baseline session define the test flow.

A confirmation message appears after conversion. For automation and mixed sessions, the message indicates whether `kobiton:scriptlessCapture` was set:

* With `kobiton:scriptlessCapture`: "Test Case converted with kobiton:scriptlessCapture! Full data captured for optimal test case."
* Without `kobiton:scriptlessCapture`: "Some session data might be limited. Add 'kobiton:scriptlessCapture' for better results next time."

When a mixed session is converted, the Test Case holds both the manual steps and the automation steps in the order they were recorded. Each step is tagged with its source, so a Revisit replays it through the matching execution path. Test Cases converted from a mixed session show *Mixed* as the Source type.

Converting a session to a Test Case unlocks additional capabilities, including running the test across other devices. Appium script generation is available only for Test Cases converted from manual sessions.

After conversion, the option to view the Test Case becomes available. Selecting this opens the Test Case details view, where the captured steps and interactions can be reviewed and managed.

== Manage Test Cases

Test Cases are managed through Test Management in the Kobiton platform.

=== Test Case list

The Test Case list provides an overview of the Test Cases available to the selected Team. To view Test Cases for another Team, switch Teams.

From this view, users can locate Test Cases, review basic information, and open individual Test Cases for detailed review and management.

The list displays all Test Cases regardless of source type. The *Source* column uses an icon to indicate whether each Test Case was created from a manual, automation, or mixed session.

image::tc-list-source.png[width=700,alt="Test Cases list showing the Source column"]

Use the search bar at the top of the list to find a specific Test Case by name. You can sort the list by name. Search and sort apply to both source types. Filtering the list by source type is not supported.

The following actions are available for each Test Case in the list:

* Select the Test Case ID to open the Test Case details view. Additional actions, such as generating an Appium script, are available there.
* *Run Test Case* — create a new Test Run from the existing definition. This action is disabled for Test Cases that a Test Run can't replay. See xref:test-management:test-cases.adoc#_test_cases_that_cant_run[Test Cases that can't run].
* *Clone Test Case* — create a duplicate that can be modified independently.
* *Delete Test Case* — remove the Test Case from the list and from any test suites it was assigned to.

To create a new Test Case from a past session, select *New Test Case* in the Test Cases view. Completed sessions that have not yet been converted are available for selection. Use a keyword search such as `type:appium` or `type:mixed` to narrow the list to a specific session type.

=== Test Case details

The Test Case details view displays the steps captured from the baseline session.

From this view, users can:

* Review captured test steps
* Remediate test steps when element selection requires correction
* Update Test Case metadata
* Assign the Test Case to one or more test suites
* Clone the Test Case
* Delete the Test Case
* Generate an Appium script

Test Case details reflect the current version of the Test Case.

If a Test Run can't replay the Test Case, *Run* is disabled on the details page. Hover over *Run* to see the reason. See xref:test-management:test-cases.adoc#_test_cases_that_cant_run[Test Cases that can't run].

==== Delete test steps

Test steps can be deleted when they are no longer needed.

. In the *Test Steps* section, select the *⋮* menu for the step you want to delete.
. Select *Delete Test Step*
. Repeat these steps for each step you want to delete.
. Select *Save*.

Changes apply only after you select *Save*. Saved changes create a new version of the Test Case. Previous versions remain available from the *Test Case Version* dropdown.

==== Edit text in test steps

Test steps that use the *Enter Text* action support inline text editing. Use this option to update the text value entered during the step.

. In the *Test Steps* section, hover over the *Enter Text* label for the step you want to update.
. In the preview window, select the edit icon.
. Update the text value.
. Select the checkmark icon to confirm the change. The edit icon changes to a checkmark while the text value is being edited.
. Select *Save*.

Changes apply only after you select *Save*. Saved changes create a new version of the Test Case.

image::tm-edit-text.png[width=700,alt="Enter text test step in edit mode with the context box open"]

[#_remediate_test_steps]
==== Remediate test steps

Test steps that use the *Touch* action can require remediation when Kobiton cannot reliably select the target element. Remediation is performed from Session Explorer and updates the Test Case definition.

From the Test Case details page, you can open remediation for an individual touch step. In the step list, select the *⋮* menu next to the step, then select *Remediate Test Step*. If the step was previously remediated, select *Edit Remediation*.

For the full procedure, see xref:test-management:remediations.adoc[Remediations].

After you save the remediation, Kobiton creates a new version of the Test Case.

[#_test_cases_that_cant_run]
== Test Cases that can't run

A Test Run replays a Test Case by installing or opening the app recorded in the baseline session. Kobiton blocks a Test Case from running when the recording doesn't give a Test Run an app it can install or open:

* *App not installed from the app repository.* The app was uploaded from a local file during a manual session, or installed from a URL in the `app` capability of an automation session.
* *Device home screen only.* The recording only uses the device home screen.
* *No app or browser under test.* The recording has no app or browser under test.

Test Cases whose app was installed from the app repository run as before. Test Cases that open an app or browser without installing it, such as Chrome, also run as before.

=== How blocked Test Cases appear

* In the Test Case list, *Run Test Case* is disabled. Hover over it to see the reason.
* On the Test Case details page, *Run* is disabled and shows the reason as a tooltip.
* On the Test Run Setup screen, the Test Case shows an alert icon with the reason and can't be selected.
* In *Customize* for a Test Suite, a blocked Test Case version shows an alert icon in the version dropdown and can't be selected.

Editing, cloning, deleting, and Appium script generation stay available for these Test Cases. Test Cases labeled *Unsupported* because of their steps keep their current behavior and messages.

=== Fix a blocked Test Case

Record the Test Case again so that a Test Run can replay it. The tooltip states the fix for each reason:

[cols="1,3"]
|===
| Reason | Tooltip

| App not installed from the app repository, manual session
| This test case can't run because its app wasn't installed from the app repository during recording. Upload the app to the app repository, install it from there in a new session, and record the test case again.

| App not installed from the app repository, automation session
| This test case can't run because its app wasn't installed from the app repository during recording. Upload the app to the app repository, then record the test case again with the app capability set to kobiton-store:v<appVersionId>.

| Device home screen only
| This test case only uses the device home screen. Record it again and open the app or browser you want to test.

| No app or browser under test
| This test case has no app or browser under test. Record it again and open the app or browser you want to test.
|===

For automation sessions, set the `app` capability to `kobiton-store:v<appVersionId>`, where `<appVersionId>` is the app version ID from the app repository.

=== API and MCP behavior

Creating a Test Run through the API (`POST /v2/test-runs`) or the `createTestRun` MCP tool returns a `400` error when any selected Test Case version is blocked. No executions are created. The error message names the Test Case ID and version and includes the same reason and fix as the tooltip.

Test Case reads in the API return a `run_blocked_reason` field for each Test Case version. The value is `null` when the version can run.

[#_test_cases_from_automation_sessions]
== Test Cases from automation and mixed sessions

Test Cases created from automation and mixed sessions appear in the Test Case list alongside those created from manual sessions and support the same core actions, including run, clone, delete, tag, versioning, and assignment to test suites. The following behavior is specific to these Test Cases. For Test Cases created from mixed sessions, step-level behavior applies to the automation steps.

=== Source type

In the Test Case details view, the info bar shows *Source Type: Automation*, *Source Type: Mixed*, or *Source Type: Manual*, depending on the session the Test Case was created from. The adjacent *Source* field links to the originating session in Session Explorer.

image::tc-details-infobar.png[width=700,alt="Test Case details info bar with Source and Source Type"]

=== Supported apps

Only apps from *App Repo* and *Existing Apps* are supported for automation-sourced Test Cases.

Only the app installed at session start is captured. Apps installed later in the session are not captured, and the corresponding steps are labeled *Unsupported* after conversion.

=== Test step names

Test step names follow the action path of the automation step. When a step name is too long to display in full, the complete name is available in a tooltip.

=== Unsupported steps

An automation session can include actions that are not supported for conversion. A step that maps to an unsupported endpoint is labeled *Unsupported* in the Test Case details view.

When you convert a mixed session, only its Appium automation steps convert. Steps from other automation types, such as XCUITest, UIAutomator, or Espresso, are labeled *Unsupported*. Unsupported steps don't block conversion.

=== Element selection remediation

Touch actions captured with screen coordinates can be remediated when element selection needs correction. Remediating a step updates the Test Case definition and the step name. For the procedure, see xref:test-management:remediations.adoc[Remediations].

=== Appium script generation

Appium script generation is not available for Test Cases created from automation or mixed sessions. The control is disabled and displays the tooltip: "Generating Appium scripts is not supported for test cases converted from automation sessions".

== Editing and versioning

Changes to a Test Case create new versions.

Versioning allows Test Cases to evolve as applications change while preserving previous definitions. Execution results remain associated with the version used at the time of execution.

To view a previous version, open the Test Case details page, then select a version from the *Test Case Version* dropdown.

Versions are listed chronologically, with the oldest version first and the newest version last.

[NOTE]
====
Changes to Test Case steps apply only after you select *Save*. Saving changes creates a new version of the Test Case. Previous versions remain available from the *Test Case Version* dropdown.
====

== Generate an Appium script

An Appium script can be generated from a Test Case.

From the Test Case details view, users can generate an Appium script based on the captured interactions in the Test Case. This script represents the same test flow and can be used as a starting point for script-based automation.

=== When it’s used

Generated Appium scripts are typically used when test definitions need to be extended, customized, or integrated into script-based automation workflows.

Using Scriptless automation does not require generating or maintaining Appium scripts.

If a Test Case is modified after an Appium script has been generated, the script must be regenerated to reflect the updated changes.

[NOTE]
====
Appium script generation is available only for Test Cases created from manual sessions. For Test Cases created from automation or mixed sessions, the control is disabled. See xref:test-management:test-cases.adoc#_test_cases_from_automation_sessions[Test Cases from automation and mixed sessions].
====

For supported languages and frameworks, see xref:test-management:generate-appium.adoc[Generate an Appium script].
